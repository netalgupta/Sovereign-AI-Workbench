# Wiring the graph explorer and knowledge base into the app

These two pages were built on `aryan/rag-and-graphrag`, which has no
`frontend/` of its own — the app shell, router and design tokens live on
`advay/frontend`. They are written to that branch's conventions (named
exports, `var(--color-*)` tokens, `lucide-react` icons, Tailwind
utilities) so they drop in without modification.

**They are not yet routed.** `App.jsx` is owned by the frontend branch;
editing it here would create a merge conflict on a file whose other 40
lines this branch has no business touching. So the routing change is
written down instead of made:

```diff
- import { GraphStubPage }   from './pages/GraphStubPage'
- import { SourcesStubPage } from './pages/SourcesStubPage'
+ import { GraphExplorerPage }   from './pages/GraphExplorerPage'
+ import { KnowledgeBasePage }   from './pages/KnowledgeBasePage'
+ import { InstrumentationPage } from './pages/InstrumentationPage'

-        <Route path="/graph"           element={<GraphStubPage />} />
-        <Route path="/sources"         element={<SourcesStubPage />} />
+        <Route path="/graph"           element={<GraphExplorerPage />} />
+        <Route path="/sources"         element={<KnowledgeBasePage />} />
+        <Route path="/instrumentation" element={<InstrumentationPage />} />
```

`/instrumentation` is a NEW route (the others fill existing stubs), so it
also needs a nav entry in `AppShell.jsx`. It is the one-stop view — every
other page above is a focused slice of what it shows.

Both routes already exist in `App.jsx` with stubs reserved for them
(`/graph` — "Knowledge Graph Explorer … Day 8", `/sources` — knowledge
base manager), so this fills planned scope rather than adding new
surface. The stub files can be deleted once the routes are switched.

## Design tokens these pages expect

They read existing `--color-*` tokens, plus five for graph node labels.
Add to the same `:root` blocks that define the rest of the palette, in
**both** themes:

```css
--graph-equipment: #c26a10;   /* dark: #e2941f */
--graph-segment:   #12798c;   /* dark: #3fb2c6 */
--graph-document:  #5b5f9e;   /* dark: #8f93d6 */
--graph-incident:  #a63927;   /* dark: #d2705c */
--graph-person:    #2f7a52;   /* dark: #5aab7c */
```

`ForceGraph` reads these through `getComputedStyle` on every frame, so
they follow a theme switch live with no re-render. If a token is
missing the node falls back to grey rather than disappearing.

## Data

Both pages `fetch()` from `/pipeline/*.json`, static snapshots exported
by the backend:

```bash
python -m backend.evaluation.export_inspection_data   # graph + chunks + embeddings
python -m backend.evaluation.export_image_data        # images + OCR + chart readings
python -m backend.evaluation.export_frontend_assets   # writes frontend/public/pipeline/
```

Static rather than live because no backend HTTP endpoint exists for the
graph or the vector store yet. Shipping a working explorer over a real
exported graph beats shipping a stub that waits for an API. When the
endpoints land, change the `fetch` URL in each page — one line each,
nothing else in these files assumes a static file.

`graph.json` and `chunks.json` are committed (34 KB and 28 KB).
`images.json` is **not** — it is ~3.3 MB of base64 chart images derived
entirely from PNGs already tracked under `MRPL_Chart_Stress_Corpus/` and
`MRPL_RAG_Test_Corpus/`, so it is gitignored and regenerated by the
command above. The Images tab degrades to an empty state without it
rather than breaking.

## Verification status — read this before assuming it works

The components are written against the target branch's conventions but
have **not been run**: this branch has no `frontend/`, so there is no
`package.json` to install and no dev server to start here. They compile
as far as syntax, and the data files they load are real exports with the
shapes the code expects, but nothing has rendered them in a browser.
First run after the merge should be treated as a first run, not a

## Backend API

`InstrumentationPage` and `pipelineApi.js` talk to the FastAPI backend:

```bash
python -m uvicorn backend.main:app --host 127.0.0.1 --port 8000
```

Bound to loopback deliberately — this API reads the user's filesystem and
has no authentication, so it must not appear on a plant network. CORS is
restricted to the Vite dev origins for the same reason.

| route | serves |
|---|---|
| `GET /api/health` | per-dependency status (graph up? corpus loaded? how many images?) |
| `GET /api/graph` | all nodes + relationships, live from Neo4j |
| `GET /api/chunks` | chunks, metadata, PCA coords, similarity matrix |
| `GET /api/images` | every stored image + OCR + reading (pixels NOT inlined) |
| `GET /api/images/{id}/raw` | the actual pixels |
| `POST /api/images/select` | pick the right image for a request |
| `GET /api/metrics` | every measured evaluation result, each with `measured_at` |
| `GET /api/sources` / `POST` / `DELETE` | watched folders, registry, queue |
| `POST /api/sources/scan` | scan and enqueue, newest first |
| `POST /api/search` | grounded retrieval, or an explicit refusal |
| `GET /api/preview` | one rendered page + highlight rects |

Override the base URL with `VITE_API_BASE` if the backend runs elsewhere.

### The client falls back, on purpose

`pipelineApi.js` tries the API and falls back to the static
`/pipeline/*.json` snapshots when it is not running. The frontend and
backend are separate processes a developer starts separately, and a UI
showing nothing but a connection error is useless exactly when you are
working out which one is down. **Every result carries `source`**
(`api` / `snapshot` / `unavailable`) and the UI prints it — showing a
stale export as live data is the same failure as citing a document that
has since been edited.
