## 1. Orchestrator & Agent Framework

### Q1: Is the orchestrator LangGraph specifically, or something else? Single graph with conditional routing, or a supervisor dispatching to sub-agent graphs?
* **Framework**: It is **LangGraph specifically** (`langgraph.graph.StateGraph` backed by Pydantic `AgentState`).
* **Graph Topology**: Currently structured as a **single compiled graph with conditional routing**:
  ```
  [router / safety interlock]
           │
           ├── (Action approval required?) ──► [END / Await Operator Modal]
           │
           └── (Standard Query) ──► [planner] ──► [dispatch loop] ──► [synthesize] ──► [verify] ──► END
  ```
  *(See [`backend/orchestrator/graph.py:L277-L301`](file:///Users/aditya4/Desktop/SIH26117-Sovereign-Workbench/backend/orchestrator/graph.py#L277-L301))*
* **Supervisor Dispatch Loop**: Inside `dispatch_node`, the orchestrator acts as an iterative supervisor. It inspects `state.ready_steps()` from the DAG generated by `planner_node`, respects step dependencies (`depends_on`), and dispatches tasks to sub-agents until all DAG nodes reach `status: "done"`.

### Q2: How does a sub-agent currently get invoked — as a graph node calling an LLM directly, or as a "tool" the top-level agent calls (i.e. is there already a pattern for "agent-as-tool")?
* Sub-agents are currently invoked as **deterministic Python worker functions** dispatched by `dispatch_node` in [`backend/orchestrator/dispatch.py`](file:///Users/aditya4/Desktop/SIH26117-Sovereign-Workbench/backend/orchestrator/dispatch.py):
  * `retrieval_agent`: Calls `retrieve_with_grounding_check()` directly against the FAISS vector store.
  * `math_tool`: Direct deterministic function call (`call_tool_as("math_tool", ...)`). **NFR-5 strictly forbids routing arithmetic to an LLM**.
  * `code_agent`: Invokes the warm Docker sandbox pool (`run_in_sandbox()` or async `run_code_step()`).
  * `vision_agent`: Calls Ollama `qwen2.5vl:7b` through vision tools (`chart_understanding.py`).
  * `reasoning_agent`: Prompts `qwen2.5:14b` for summarization and drafting.
* **Pattern**: It operates as an **agent-as-worker / tool-executor pattern** enforcing strict role-based tool access contracts (`_ALLOWED_TOOLS` in `dispatch.py`). Sub-agents are not yet separate nested LangGraph subgraphs, but function as modular units with defined contracts.

### Q3: Is there already a distinction in your system between a "tool call" (one LLM turn, structured output) and a "sub-agent" (multi-turn loop with its own tool access)? Which one would a multi-stage thing like slide planning → render → QA → retry naturally become?
* **Existing Distinction**:
  * **`ToolCallEvent`**: Represents a single execution of an underlying tool with `tool_name`, `input_params`, `output`, `status`, and `timestamp` ([`backend/orchestrator/state.py:L14-L24`](file:///Users/aditya4/Desktop/SIH26117-Sovereign-Workbench/backend/orchestrator/state.py#L14-L24)).
  * **`PlanStep`**: A unit of work in the planner DAG assigned to an agent (`assigned_agent: "code" | "retrieval" | "vision" | "math" | "reasoning"`), carrying dependencies (`depends_on: list[str]`).
* **Natural Fit for Slide Planning → Render → QA → Retry**:
  * It naturally becomes a **dedicated LangGraph Subgraph** OR a **specialized Sub-Agent with an internal loop**.
  * **Recommended Structure**: A dedicated `slide_generation_subgraph` (or `code_agent` workflow) that:
    1. Plans slide structure and layout (LLM turn with structured JSON schema).
    2. Acquires the session's warm Docker sandbox worker once.
    3. Renders the slides (`python-pptx`).
    4. Executes QA (heuristic overflow/contrast checks + `qwen2.5vl` visual critique).
    5. Retries in-place within the same container if defects are found.
    6. Returns the final deck artifact and citations.

### Q4: How is conversation/task state persisted across a multi-step job like this — LangGraph checkpointer, a DB row, in-memory only?
* **Current State**: **In-memory only per turn** inside `AgentState`.
  * `run_agent_turn(message, session_id)` in [`backend/orchestrator/graph.py:L313-L325`](file:///Users/aditya4/Desktop/SIH26117-Sovereign-Workbench/backend/orchestrator/graph.py#L313-L325) instantiates `AgentState` on invocation. LangGraph Checkpointers (e.g., `MemorySaver`, `SqliteSaver`) are not yet attached to `build_orchestrator_graph()`.
* **Multi-Turn Chat History**: Stored client-side in the Zustand store ([`frontend/src/store/chatStore.js`](file:///Users/aditya4/Desktop/SIH26117-Sovereign-Workbench/frontend/src/store/chatStore.js)) and passed via `POST /api/chat`.
* **Audit State**: Safety-critical events, approvals, and tool executions are persisted to disk in the append-only JSONL log ([`backend/audit/audit.jsonl`](file:///Users/aditya4/Desktop/SIH26117-Sovereign-Workbench/backend/audit/audit_log.py)).

## 2. RAG & Document Ingestion

### Q5: What's the vector store (Chroma, FAISS, pgvector, Qdrant, other) and is it one shared index or per-document-set?
* **Store**: **FAISS (`IndexFlatIP`, 1024 dimensions) + SQLite metadata table** ([`backend/retrieval/vector_store.py:L1-L59`](file:///Users/aditya4/Desktop/SIH26117-Sovereign-Workbench/backend/retrieval/vector_store.py#L1-L59)).
* **Index Architecture**: **One shared index** for all ingested corpus documents.
  * Vectors are indexed in FAISS using inner product (equivalent to cosine similarity because vectors are unit L2-normalized).
  * Text, document paths, types, page numbers, and chunk indices are stored in a parallel SQLite table keyed by the FAISS ID.
  * State can also be hydrated instantly from the precomputed snapshot `backend/evaluation/inspection_data.json` for sub-second startup.

### Q6: What's the embedding model, and does the same GPU budget apply to it (does it need to be loaded/unloaded around your generation LLM)?
* **Model**: **`BAAI/bge-large-en-v1.5`** (1024-dimensional dense vectors) via HuggingFace `SentenceTransformer` ([`backend/ingestion/embeddings.py`](file:///Users/aditya4/Desktop/SIH26117-Sovereign-Workbench/backend/ingestion/embeddings.py)).
* **Offline / Zero-Download Fallback**: If the local HuggingFace cache is unpopulated, it transparently runs `_deterministic_embed()` (token and n-gram hash projection to 1024-d unit sphere), requiring 0 network downloads.
* **GPU Budget**:
  * The GPU budget (targeted for RTX 4060 8GB) is dedicated to Ollama LLMs (`qwen2.5:14b` / `qwen2.5-coder:7b`).
  * `SentenceTransformer` embeddings run comfortably on **CPU**, so **no GPU unloading/reloading cycles are required** around the generation LLM.

### Q7: What's the chunking strategy, and does a chunk carry enough metadata (source doc, page, section heading) to cite back to on a slide?
* **Strategy**: `RecursiveCharacterTextSplitter.from_tiktoken_encoder` with `cl100k_base` encoding, **512 tokens chunk size**, and **64 tokens overlap** ([`backend/ingestion/chunking.py:L24-L32`](file:///Users/aditya4/Desktop/SIH26117-Sovereign-Workbench/backend/ingestion/chunking.py#L24-L32)).
* **Metadata Fields** (`ChunkMetadata` in [`backend/ingestion/document_ingestion.py:L26-L47`](file:///Users/aditya4/Desktop/SIH26117-Sovereign-Workbench/backend/ingestion/document_ingestion.py#L26-L47)):
  * `source_document: str` (e.g. `SOP-114-Rev3_Hydrocracker.docx`)
  * `document_type: str` (e.g. `pdf`, `docx`, `xlsx`)
  * `page_number: int | None` (page number for PDFs; `None` for unpaginated text/DOCX)
  * `chunk_index: int`
  * `ingestion_date: str`
  * `image_ids: list[str]` (SHA-256 hashes of any diagrams/charts appearing on that page)
* **Section Headings**: Headings are preserved verbatim inside the chunk text itself (via markdown/DOCX extraction), but there is no dedicated isolated `section_heading` metadata column.

### Q8: What document types are already ingested — anything where "put this on a slide" is nontrivial (tables, charts already embedded in a source PDF)?
* **Supported & Detected Formats** ([`backend/ingestion/document_types.py`](file:///Users/aditya4/Desktop/SIH26117-Sovereign-Workbench/backend/ingestion/document_types.py)):
  * `PDF`: Extracted via PyPDF / pdfplumber with PaddleOCR / Tesseract fallback for scanned pages.
  * `DOCX`: Paragraphs and tables extracted via `python-docx`.
  * `XLSX / XLS`: Worksheets, tables, and cell formulas extracted via `openpyxl`.
  * `CSV / TSV`: Formatted tabular data.
  * `Images` (`PNG`, `JPG`, `TIFF`, `BMP`): Handled via PaddleOCR / vision pipeline.
  * `Audio` (`WAV`, `MP3`, `M4A`): Transcribed via faster-whisper.
* **Non-Trivial Visual Content ("Put this on a slide")**:
  * **Embedded PDF Images**: The system includes a dedicated `ImageStore` ([`backend/ingestion/image_store.py`](file:///Users/aditya4/Desktop/SIH26117-Sovereign-Workbench/backend/ingestion/image_store.py)) and `image_retrieval.py` that extracts diagrams, P&ID schematics, and letterhead logos by SHA-256 content hash and attaches them to chunks.
  * These raw image bytes can be retrieved by `image_id` and embedded directly onto a generated PowerPoint slide.

### Q9: Is retrieval currently a single top-k similarity call, or does it already do query rewriting / multi-hop / reranking?
* **Retrieval Mode**: **Single hybrid search call** with confidence gating ([`backend/retrieval/grounded_retrieval.py`](file:///Users/aditya4/Desktop/SIH26117-Sovereign-Workbench/backend/retrieval/grounded_retrieval.py)):
  * Computes dense FAISS cosine similarity + sparse BM25 lexical match.
  * Combines ranks via Reciprocal Rank Fusion (RRF).
  * Applies an explicit grounding gate (`MIN_RETRIEVAL_SIMILARITY = 0.40`). If below threshold, refuses rather than hallucinating.
* **Implication for Slides**: It does **NOT** do automated multi-hop query decomposition or multi-query expansion. The slide planning agent should perform **iterative, per-section / per-topic retrieval calls** rather than a single monolithic prompt query.

## 3. Code Execution & Docker Sandbox

### Q10: What's actually in the sandbox image — Python only, or Node too?
* **Image**: Built from `nikolaik/python-nodejs:python3.11-nodejs20-slim` ([`backend/sandbox/Dockerfile.sandbox`](file:///Users/aditya4/Desktop/SIH26117-Sovereign-Workbench/backend/sandbox/Dockerfile.sandbox)).
* **Runtimes**: **Both Python 3.11 AND Node.js 20** are present.
* **Pre-Installed Libraries**:
  * Python: `pandas`, `numpy`, `sympy`, `matplotlib`, `scipy`, `scikit-learn`, `xgboost`, `seaborn`, `plotly`, `networkx`, `pypdf`, `python-docx`, `openpyxl`, `beautifulsoup4`, `pyyaml`, `markdown`, `pillow`, `regex`, `jsonschema`.
* **Renderer Decision**:
  * `python-docx` is pre-installed.
  * **`python-pptx` is NOT currently in `Dockerfile.sandbox`** (nor is `pptxgenjs` in npm).
  * Adding `python-pptx==1.0.2` to `Dockerfile.sandbox` is a quick 1-line update.

### Q11: How does the calling agent get code into the sandbox and results out — write a script to a shared volume and exec, or an API/RPC into the container?
* **Code Ingress**:
  * The host directory `SESSIONS_HOST_DIR` (`/tmp/sandbox_sessions/<session_id>/`) is bind-mounted `rw` into the container at `/sandbox/sessions/<session_id>/` ([`backend/sandbox/pool.py:L142`](file:///Users/aditya4/Desktop/SIH26117-Sovereign-Workbench/backend/sandbox/pool.py#L142)).
  * The executor writes `script.py` to the host directory ([`backend/sandbox/executor.py:L33-L40`](file:///Users/aditya4/Desktop/SIH26117-Sovereign-Workbench/backend/sandbox/executor.py#L33-L40)).
* **Execution**: Executed via Docker API: `client.api.exec_create()` and `client.api.exec_start(stream=True, demux=True)`.
* **Results Egress**:
  * Real-time stdout/stderr streams are read directly from the socket stream and forwarded over WebSocket.
  * Any output files (e.g. `.pptx`, `.docx`, `.png`) written to the current working directory (`/sandbox/sessions/<session_id>/`) **instantly appear on the host filesystem** at `/tmp/sandbox_sessions/<session_id>/` with zero copy overhead.

### Q12: Is the sandbox spun up fresh per task or is there a warm pool?
* **Pool Architecture**: Managed by a **pre-warmed Worker Pool** (`backend/sandbox/pool.py`, default 4 workers).
* **Lifecycle**:
  * Workers run `sleep infinity` from app startup.
  * Workers are **stickily bound to a `session_id`** for up to 15 minutes of idle time (`SESSION_IDLE_TIMEOUT_SECONDS = 900`).
* **Implication**: Inside one chat session, executing code pays **only a fast process fork cost (`docker exec` ~15ms)**, NOT a container startup cost (`docker run`). A multi-stage *Render → QA → Re-render* loop inside the same session is extremely fast and cost-effective.

### Q13: Is `--network none` the only enforcement, or is there also a syscall/seccomp restriction? Does the sandbox have LibreOffice (`soffice`) and `pdftoppm`/Poppler available for pptx→image QA rendering, or would that need adding to the image?
* **Security Hardening**:
  * `network_disabled=True` (`--network none`)
  * `read_only=True` (immutable root filesystem)
  * `tmpfs={"/tmp": "size=64m"}`
  * `mem_limit="512m"` and `nano_cpus=1_000_000_000` (1 CPU core)
  * `cap_drop=["ALL"]` (drops all Linux capabilities)
  * `security_opt=["no-new-privileges"]`
  * `user="1000:1000"` (`sandboxuser`, non-root)
* **Rendering Utilities (`soffice`, `pdftoppm`)**:
  * **Neither LibreOffice nor Poppler is currently in the image**.
  * If the pipeline converts PPTX → PDF → PNG for visual QA, `libreoffice-nogui` and `poppler-utils` must be added to `Dockerfile.sandbox`. Alternatively, visual layout checks can be run heuristically on slide elements in Python before export.

### Q14: Can the sandbox read from the RAG store / vector DB directly, or does context have to be fully resolved and passed in as text/JSON before the code runs?
* **No Direct Access**: Due to strict air-gapping (`--network none`, read-only root, no volume mount to SQLite/FAISS), the container **cannot reach the vector database**.
* **Context Transfer**: All context, facts, numbers, and citations must be resolved upstream by the orchestrator and passed into the sandbox either as script arguments/variables or written to a JSON file (e.g. `/sandbox/sessions/<session_id>/context.json`).

## 4. Model Registry & Local Models

### Q15: What models are in `models.yaml` today, and does any of them support constrained/structured JSON decoding (grammars, guided decoding) — or would that need to be added for reliable schema output?
* **Registry** ([`models/models.yaml`](file:///Users/aditya4/Desktop/SIH26117-Sovereign-Workbench/models/models.yaml)):
  ```yaml
  - id: coder-model
    backend: ollama
    model: qwen2.5-coder:7b
    task_tags: [code_generation, code_review, debugging]

  - id: reasoning-model
    backend: ollama
    model: qwen2.5:14b
    task_tags: [summarization, drafting, approval_notes, planning]

  - id: vision-model
    backend: ollama
    model: qwen2.5vl:7b
    task_tags: [ocr, image_understanding, diagram_reading]

  - id: fast-router
    backend: ollama
    model: phi-3.5-mini
    task_tags: [classification, routing]
  ```
* **Structured JSON Decoding**:
  * Ollama natively supports `"format": "json"` as well as strict Pydantic JSON schemas via GBNF grammars under the hood.
  * Currently, our caller functions (`planner.py`, `router.py`) do standard HTTP POST requests and regex parsing.
  * Adding `"format": SlideDeckPlan.model_json_schema()` to the Ollama payload can be enabled immediately for reliable schema compliance.

### Q16: Is there a local vision-capable model available at all (for the visual QA step), or would that QA stage have to be purely heuristic (overflow/contrast checks) with no model-in-the-loop?
* **Yes, a local vision model is available**: **`qwen2.5vl:7b`** (`vision-model`).
* **Active Vision Implementation**: The codebase already integrates this model in [`backend/tools/vision/chart_understanding.py`](file:///Users/aditya4/Desktop/SIH26117-Sovereign-Workbench/backend/tools/vision/chart_understanding.py), sending base64 images directly to Ollama.
* **Hybrid Visual QA Recommendation**:
  1. **Heuristic QA**: Fast bounding-box overlap checks, text-length overflow checks, and font size limits in Python.
  2. **Model QA (`qwen2.5vl:7b`)**: Qualitative layout assessment (visual hierarchy, image placement, readability) for final signoff.

### Q17: Roughly what context window do your working models have — does it comfortably fit "retrieved chunks + slide schema + few-shot layout examples" per planning call, or does the outline need to be built slide-by-slide to stay small?
* **Model Context Capacities**:
  * `qwen2.5:14b` and `qwen2.5-coder:7b` support up to **32k (and 128k)** tokens.
  * In local Ollama on an 8GB VRAM card (RTX 4060), running at `num_ctx: 8192` or `16384` is standard and stable.
* **Planning vs. Generation Strategy**:
  * **Deck Outline & Section Plan**: Comfortably fits in a single planning turn (retrieved chunks + deck-level schema + few-shot outline fits within 4k-8k tokens).
  * **Slide Content & Code Generation**: Best generated **slide-by-slide or section-by-section**. Generating 10+ slides in a single code completion frequently causes local 7B/14B models to drop boilerplate, truncate shapes, or omit formatting.

## 5. Approval Gate & Audit

### Q18: Does the human-approval-gate today block on a UI action (Electron frontend has an approve/reject button) or is it a CLI/file-based confirmation? Would a rendered slide preview need to go through the same channel as, say, an SAP write approval, or does it need its own review UI (e.g. showing thumbnail images)?
* **Gate Mechanism**: Blocks on an interactive **UI Modal** in the frontend ([`frontend/src/components/workbench/ApprovalModal.jsx`](file:///Users/aditya4/Desktop/SIH26117-Sovereign-Workbench/frontend/src/components/workbench/ApprovalModal.jsx)).
  * When `awaiting_human_approval: True` is returned, the UI displays an amber/red safety interlock modal with "Authorize Action" and "Reject Action" buttons that POST to `/api/approvals/resolve`.
* **Channel Separation**:
  * **Safety Gate Channel**: Reserved strictly for hazardous control actions (DCS setpoint changes, SAP write commands, safety interlocks).
  * **Deliverable Review Channel**: A presentation or report is a safe deliverable. It should **not** trigger the safety interlock modal.
  * Instead, it connects to the **Outputs Library / Output Cards UI** ([`frontend/src/integrations/output-cards/RealOutputCards.jsx`](file:///Users/aditya4/Desktop/SIH26117-Sovereign-Workbench/frontend/src/integrations/output-cards/RealOutputCards.jsx)), which renders a file card with thumbnail preview, citation count badge, and a **Download** button.

### Q19: Does the audit module log tool inputs/outputs already, or just pass/fail of the approval gate?
* **Both are logged**:
  1. **Persistent Audit Log** ([`backend/audit/audit_log.py`](file:///Users/aditya4/Desktop/SIH26117-Sovereign-Workbench/backend/audit/audit_log.py)): Logs `APPROVAL_REQUESTED`, `APPROVAL_GRANTED`, `APPROVAL_REFUSED`, `TOOL_EXECUTED`, `TOOL_FAILED`, and `CORRECTION` with actor, timestamp, and a full `details: dict[str, Any]` payload.
  2. **In-Memory Turn Log** (`ToolCallEvent` in [`backend/orchestrator/state.py`](file:///Users/aditya4/Desktop/SIH26117-Sovereign-Workbench/backend/orchestrator/state.py)): Records exact `tool_name`, `input_params`, and `output` dictionary for every tool call executed during the turn, returned directly to the frontend chat trace.
  * The entire numeric-tool-call → chart-value → slide-bullet chain is fully auditable.

## Summary Matrix for Slide Pipeline Implementation

| Dimension | Architectural Decision for Slide Pipeline |
|---|---|
| **Pipeline Integration** | Implement as a dedicated LangGraph Subgraph (`slide_agent`) called by `dispatch_node`. |
| **Retrieval Strategy** | Multi-turn retrieval loop: retrieve per slide section rather than single monolithic query. |
| **Sandbox Execution** | Acquire session's warm container once via `pool.acquire(session_id)`. Run Python script generating `.pptx`. |
| **Rendering Library** | `python-pptx` (add to `Dockerfile.sandbox`). |
| **QA Loop** | Heuristic bounds & font overflow checks in Python + optional `qwen2.5vl:7b` visual pass; retry inside same warm worker. |
| **UI Delivery** | Stream logs over `/ws/session/{session_id}`; present final deliverable in `RealOutputCards.jsx` with Download button. |
